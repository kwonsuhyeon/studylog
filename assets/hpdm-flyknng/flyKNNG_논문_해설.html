Zhuoran Ji, Cho-Li Wang. Efficient Exact K-Nearest Neighbor Graph Construction for Billion-Scale Datasets using GPUs with Tensor Cores. ICS '22. doi:10.1145/3524059.3532368

GPU 기초, 거리 항등식, Algorithm 1 한 줄씩 읽기는 배경지식 노트에 있다. 이 해설은 그다음 단계로 3절의 설계 이유, 4절의 top-k 알고리즘, 5절의 실험을 다룬다.

수치는 원문 기준이다. 정렬 예제의 숫자는 직접 만들어 Python으로 검증했다. 원문에 없는 해석에는 추론이라고 적었다.

해설 지도

이 논문의 아이디어는 세 개다. ① 거리 계산을 Tensor Core 행렬곱으로 한다. ② top-k를 같은 커널에서 바로 처리해 거리 행렬을 저장하지 않는다. ③ 그 top-k는 register 안에서 bitonic 정렬로 처리하고, 갱신할 필요가 없으면 warp 단위로 통째로 건너뛴다. ①은 기존에도 쓰던 방법이다. 이 논문의 새로운 점은 ②와 ③을 함께 설계(co-design)했다는 데 있다.

거리 행렬과 Fused Kernel

🔊 듣기 E (2~4절)

원문: 3.1절, 3.2절, Figure 2.

거리 계산 자체는 행렬곱이라 새로울 것이 없다. 이 논문이 문제 삼는 것은 그 결과인 \(N\times N\) 행렬을 global memory에 쓰고 다시 읽는 비용이다. 그래서 행렬곱과 top-k를 커널 하나로 합친다.

표기 대응

원문뜻배경지식 노트
\(d[i,j]=P_i\cdot P_j\)내적 유사도. 원문은 이것을 "distance"라고 부른다 (클수록 가까움)\(S_{ij}\)
\(d^2[i,j]=\|P_i\|^2+\|P_j\|^2-2P_i\cdot P_j\)유클리드 거리 제곱\(D^2_{ij}=q_i+q_j-2S_{ij}\)
\(O(N^2D)\)거리 행렬 계산량같음
\(O(N^2)\) → \(O(kN)\)결과를 저장할 공간, 결과를 global memory에 쓰는 양같음

분리형 커널이 손해 보는 두 가지 (3.2절)

① 불필요한 global memory 접근 2번

첫 커널이 거리 행렬을 쓰고 둘째 커널이 그것을 다시 읽는다. 점이 10억 개면 거리 행렬이 엑사바이트 규모라, 이것을 쓰고 읽는 일이 전체 작업에서 큰 비중을 차지한다.

② GPU 메모리를 빼앗김

거리 행렬이 device memory를 차지하면 데이터셋 batch를 작게 잘라야 한다. batch가 많아지면 전송 비용도 늘어난다 (4절, 10절 참고).

원문은 분리형의 장점도 인정한다. 커널을 따로 두면 cuBLAS의 고도로 최적화된 GEMM을 그대로 쓸 수 있다. 그래도 저자들은 global memory에 쓰는 양을 \(O(N^2)\)에서 \(O(kN)\)으로 줄이는 쪽이 더 이득이라고 본다. 커널을 나눠야만 쓸 수 있는 세밀한 저수준 최적화를 포기하더라도 그렇다는 판단이다.

Mini-batch 처리

원문: 3.4절.

10억 점 데이터셋(DEEP1B 179GB, SIFT1B 239GB)은 GPU 메모리는 물론 호스트 메모리에도 안 들어간다. 그래서 matrixB를 디스크에서 batch 단위로 가져오고, 전송과 계산을 Ping-Pong buffer로 겹친다.

STEP 1 데이터셋 전체는 디스크에 두고 batch로 나눈다.

STEP 2 batch 하나를 디스크 → 호스트 메모리 → GPU 메모리로 옮긴다. 병목은 디스크 대역폭이다. 디스크에서 GPU로 바로 보내는 기능이 있어도 이 병목은 그대로다.

STEP 3 원래 한 번이던 Algorithm 1 커널 실행을 batch마다 한 번씩, batch 수만큼 나눠 실행한다.

STEP 4 buffer 두 개를 둔다. 하나로 지금 batch를 계산하는 동안 다른 하나로 다음 batch를 받는다. 계산이 끝나면 둘의 역할을 바꾼다.

원문은 겹치기가 효과를 보려면 계산 시간과 전송 시간이 비슷해야 한다고 단서를 단다. flyKNNG에서는 warp 하나가 점 16개의 kNN을 맡고 수천 개 warp가 동시에 돈다. 디스크에서 올라온 점 하나가 아주 여러 번(원문 표현 "tens of hundreds of times") 쓰이므로, 계산 시간이 전송 시간을 충분히 가린다는 설명이다.

10절 5.1 결과와 이어지는 부분이다. 분리형(CUML/FAISS)은 거리 행렬을 둘 공간을 GPU 메모리에 따로 남겨야 해서 batch가 작고 개수가 많다. flyKNNG는 GPU 메모리 전체를 batch에 쓸 수 있다.

Bitonic Sort 기초

🔊 듣기 F (5~6절)

원문: 4.1절의 출발점. 원문 참고문헌 [36].

bitonic 정렬은 어느 위치끼리 비교할지가 값과 상관없이 미리 정해져 있는 정렬 방법이다(이런 방식을 정렬 네트워크, sorting network라고 한다). 모든 thread가 같은 순서로 같은 비교를 하므로 GPU에서 분기가 생기지 않는다.

용어

용어뜻예
bitonic 수열한 번 증가했다가 감소하는(또는 반대) 수열1, 4, 7, 9, 6, 3
compare-and-swap (CAS)두 값을 비교해 정해진 방향(오름·내림)이 되도록 필요하면 자리를 바꾸는 연산내림차순 CAS(3, 7) → (7, 3)
stride비교하는 두 원소 사이의 간격stride 4면 0번과 4번, 1번과 5번 …

8개 값 정렬 STEP (직접 만든 예, 최종 내림차순)

입력: [3, 7, 4, 8, 6, 2, 1, 5]. 정리된 구간의 길이를 2 → 4 → 8로 늘려 가고, 길이마다 stride를 절반씩 줄이며 비교한다.

n개를 정렬하면 비교 단계 수는 \(\log_2 n\,(\log_2 n+1)/2\)이다. 8개면 6단계로, 위 표의 줄 수와 같다. 비교 횟수는 퀵 정렬보다 많다. 대신 비교 순서가 고정되어 있어 GPU에 유리하다.

이미 bitonic인 수열은 stride를 절반씩 줄여 가며 한 번씩만 비교하면 정렬된다 (위 표의 길이 8 단계). 7절 Algorithm 3이 이 성질을 이용한다. 기존 top-k(내림차순)와 새 거리(오름차순)를 이어 붙이면 그 자체로 bitonic 수열이 되기 때문이다.

Algorithm 2: tile-major 배치 그대로 정렬

원문: 4.1절, Algorithm 2, Figure 1, Figure 3.

Tensor Core 결과(outC)는 warp의 32개 thread register에 tile-major로 흩어져 있다. Algorithm 2는 이 값을 shared memory로 옮기지 않고 register 안에서 바로 bitonic 정렬한다. thread 안의 비교는 일반 CAS로, thread 사이의 비교는 warp shuffle로 처리하고 shuffle 횟수를 최소로 줄였다.

shuffle은 모두 3번이다. 원문의 "만들기 1번 + 정렬 2번"과 같다. 길이 8 단계의 stride 4가 Algorithm 2의 15~17행(cross_cas(R[], ord, 1))이고, 정렬 단계의 stride 8과 4가 6·7행(cross_cas(…, 2), cross_cas(…, 1))이다. 나머지 비교는 모두 같은 thread의 register끼리라 통신이 없다.

func cross_cas(R[], isDec, off)          // thread 사이 비교: shuffle 1번
    for i in 0 … 4n-1:
        tmp = shuffle_reg(R[i], off)      // 예: shfl_xor_sync — tid와 off를 XOR한 짝 thread의 값
        vec_cas(R[i], tmp, isDec ⊕ (tid & off))   // 짝 중 한쪽은 큰 값, 다른 쪽은 작은 값을 남김
func sort_bitonic(R[], isDec)            // bitonic 수열 → 정렬
    cross_cas(R[], isDec, 2)             // stride 8
    cross_cas(R[], isDec, 1)             // stride 4
    (나머지 stride는 thread 안 vec_cas)
func tile_major_bitonic(R[], isDec)      // 임의 값 → bitonic 수열 → 정렬
    (길이 2, 4, …, 8n 단계로 bitonic 수열 만들기, 길이 8n·stride 4n일 때만 cross_cas)
    sort_bitonic(R[], isDec)

🔊 듣기 G (7~8절)

알고리즘 내내 지키는 조건(원문 표현 invariant, 불변식)은 하나다. topk는 항상 내림차순이다. 새 거리를 오름차순으로 정렬해 topk 뒤에 붙이면 bitonic 수열이 된다. 마주 보는 값끼리 한 번 비교해 큰 쪽만 남기면 그것이 새 top-k이고, 한 번 더 정렬하면 불변식이 다시 성립한다.
func find_local_topk(outC, topk)
    for i in 0, 1:                                      // 거리 행렬의 위쪽 / 아래쪽 절반
        idx = 2i+0, 2i+1, …, 8n+2i-4, 8n+2i-3
        if all(outC[idx] < topk[-1]): continue          // pruning: topk의 최솟값보다 모두 작으면 건너뜀
        tile_major_bitonic(outC[idx], 0)               // 새 거리를 오름차순 정렬 (Algorithm 2)
        pad dummies to make topk and outC equal length
        for j in 0 … max(4n, k)-1:
            vec_cas(topk[idx[j]], outC[idx[j]], 1)     // 마주 보는 값끼리 비교, topk 쪽에 큰 값
        sort_bitonic(topk[idx], 1)                     // bitonic → 내림차순 (불변식 복구)

Warp 단위 Pruning

원문: 4.3절, Algorithm 3의 4행. 개념은 배경지식 노트 8절.

새로 계산한 거리 묶음(거리 행렬의 위쪽 또는 아래쪽 절반)이 전부 topk의 최솟값보다 작으면 warp 전체가 Algorithm 3의 정렬·병합을 건너뛴다. 거리 계산은 건너뛰지 않는다.
질문원문의 답
무엇을 건너뛰나top-k 선택만. 무차별 대입 KNNG 구축에서 거리 계산은 피할 수 없다
왜 warp 단위인가GPU는 SIMD 방식이라 값마다 따로 판정하면 divergence가 생긴다. 또 bitonic 선택은 입력 크기가 2의 거듭제곱이어야 한다
얼마나 거칠게 거르나thread마다 insertion queue를 두는 방식은 값 하나하나를 따로 판단하므로 더 많이 걸러 낸다. 대신 값 하나당 분기가 heap은 \(\log k\)개, insertion queue는 \(k\)개인데 Algorithm 3은 \(1/128\)개뿐이다
성공 확률을 높이는 장치n(한 iteration에 계산하는 B의 점 수)을 작게 둔다. 작은 묶음일수록 "전부 탈락"이 잘 일어난다. flyKNNG 타일 설계는 데이터 재사용을 해치지 않고 n을 작게 둘 수 있다 (3.3절)
비용topk 최솟값과 한 번 비교하는 고정 비용만 든다. 건너뛰기에 성공하면 compare-and-swap이 크게 준다
실제로 잘 걸리나5.1절: 실제 데이터에서 한 점은 k개 이웃과만 매우 비슷하고 대부분의 점과는 비슷하지 않다. 그렇지 않다면 최근접 이웃 탐색 자체가 의미 없다. 그래서 pruning이 많이 일어난다
pruning의 효과는 10절에서 flyKNNG와 flyKNNG-NOSKIP(pruning만 끈 버전)을 비교하면 보인다. 평균 2.47배 차이가 나고, k가 커져도 시간이 거의 늘지 않는다.

5.4 SHARED-NOSORT: shared memory를 쓰는 융합 방식의 상한

top-k에 필요한 shared memory만 잡아 두고 실제 top-k는 하지 않는 가상 구현이다. shared memory로 top-k를 하는 융합 방식은 아무리 최적화해도 이보다 빠를 수 없다. flyKNNG는 이 상한보다도 3.44배 빠르다. SHARED-NOSORT는 차원이 256인 YFCC100M에서 CUML/FAISS보다 느리다. 차원이 크고 shared memory를 빼앗겨 타일이 아주 작아지기 때문이다.

시간이 늘어나는 주된 원인은 계산량이 아니라 자원 부족이다. RTX3090은 register file이 20.5MB, shared memory가 10.25MB로 register 쪽이 더 크다. 그래서 top-k를 register에 두는 방식이 shared memory에 두는 방식보다 k가 커져도 잘 버틴다. register가 모자라면 컴파일러가 일부 변수를 device memory로 내보낸다(spilling). 이때 컴파일러는 top-k 원소 중 어느 것을 register에 남겨야 할지 정확히 판단하지 못한다. 저자들은 개선안으로 top-k 중 가장 작은 \(k'\)개(예: 64개)만 register에 두고 나머지는 device memory에 두자고 제안한다. 새 거리가 register에 있는 \(k'\)개보다 크면 그때 다음 \(k'\)개를 device memory에서 불러와 비교한다.
