주제 1 · 코드 임베딩 out-of-core 벡터 검색

GPUout-of-coreRUMMY 계열

배경과 문제

프로그래밍 수업에서 학생 코드와 비슷한 기존 풀이를 찾을 수 있으면 쓸 데가 많습니다. 이미 작성된 피드백을 재사용할 수 있고, 표절 의심 사례도 걸러낼 수 있습니다. 문항 생성 RAG의 검색 단계도 같은 구조입니다. 코드를 임베딩 모델로 벡터로 바꾸고, 질의 코드와 가까운 벡터를 찾는 벡터 검색 문제가 됩니다.

규모가 커지면 GPU 메모리가 모자랍니다. IBM CodeNet의 제출 코드 13,916,868건을 임베딩하면 크기는 다음과 같습니다.

임베딩 설정계산크기A6000(48GB) 1장 기준
768차원 · FP3213,916,868 × 768 × 4B약 42.8GB메모리 대부분 차지, 검색 작업 공간 부족
1024차원 · FP3213,916,868 × 1024 × 4B약 57.0GB메모리 초과
SIFT1B (128차원 · uint8)10억 × 128 × 1B약 128GB메모리 2.7배 초과

데이터를 CPU 메모리(host memory)에 두고 필요한 부분만 GPU로 보내면서 검색하는 방식을 out-of-core 처리라고 합니다. 이때 병목은 GPU 연산이 아니라 CPU→GPU 전송입니다. 이 문제를 다룬 논문이 RUMMY(NSDI 2024)입니다.

4-3. 전송·연산 overlap: 기다리는 시간 숨기기

방법은 이렇습니다. 데이터를 여러 조각(chunk)으로 나눈 뒤, 한 조각을 계산하는 동안 다음 조각을 전송합니다. 세탁기와 건조기를 동시에 돌리는 것과 같은 원리입니다. 이런 실행 방식을 pipelining이라고 합니다.

GPU에는 전송을 담당하는 장치(copy engine)와 계산을 담당하는 SM이 따로 있어서 두 일을 동시에 할 수 있습니다. 두 작업을 겹쳐 시키려면 CUDA stream을 씁니다. stream은 GPU에 보내는 작업 대기열입니다. 같은 stream 안의 작업은 순서대로 실행되지만 서로 다른 stream의 작업은 동시에 실행될 수 있습니다.

실제로 계산해 봅시다

데이터를 4조각으로 나눈다고 하겠습니다. 조각 하나의 전송 시간 \(t\)는 2ms, 계산 시간 \(c\)는 3ms입니다.

STEP 1 순차 실행: 전송 → 계산 → 전송 → 계산을 반복하므로 \( 4 \times (2+3) = 20 \)ms

STEP 2 overlap 실행: 첫 조각 전송(2ms)이 끝나면 계산을 시작하고, 동시에 다음 조각을 전송합니다.

주황 = 전송(T), 파랑 = 계산(C). 버퍼가 2개라 T3은 C1이 끝나 버퍼가 비는 5ms에 시작

STEP 3 일반식으로 정리하면 다음과 같습니다.

\[ T_{\text{순차}} = n(t+c), \qquad T_{\text{overlap}} \approx t + (n-1)\max(t,c) + c \]
기호의미예제 값
\(n\)조각 수4
\(t\)조각 하나의 전송 시간2ms
\(c\)조각 하나의 계산 시간3ms
\(\max(t,c)\)둘 중 느린 쪽. 이 쪽이 전체 속도를 결정3ms

예제에 넣으면 \( 2 + 3 \times 3 + 3 = 14 \)ms이고, 순차 실행보다 \( 20/14 \approx 1.43 \)배 빠릅니다.

overlap은 전송과 계산 중 짧은 쪽을 가려 주는 기법입니다. 줄어드는 시간에는 한계가 있어서 전송이 계산보다 훨씬 길면 아무리 겹쳐도 전체 시간은 전송 시간과 비슷해집니다. RUMMY가 overlap과 함께 전송량 자체를 줄이는 기법(중복 전송 제거)을 쓰는 이유입니다.

4-4. 부하 불균형: 가장 늦게 끝나는 SM이 전체 시간을 정한다

GPU는 block들을 여러 SM에 나눠 실행합니다. 일을 다 끝낸 SM이 있어도, 가장 많은 일을 받은 SM이 끝나야 kernel 전체가 끝납니다. 일이 고르게 나뉘지 않은 상태를 부하 불균형(load imbalance)이라고 합니다.

실제로 계산해 봅시다

SM 4개에 IVF cluster 4개를 하나씩 맡깁니다. cluster 크기는 벡터 100, 20, 20, 20개이고, 벡터 하나를 처리하는 데는 1단위 시간이 걸린다고 봅니다.

STEP 1 전체 시간 = 가장 큰 일 = 100

STEP 2 실제 한 일의 총량은 \(100+20+20+20=160\)입니다. SM 4개가 100만큼 시간을 썼으니 활용률은 다음과 같습니다.

\[ \text{활용률} = \frac{\text{총 작업량}}{\text{SM 수} \times \text{전체 시간}} = \frac{160}{4 \times 100} = 40\% \]

STEP 3 큰 cluster를 40, 40, 20으로 쪼개면 일은 40, 40, 20, 20, 20, 20의 6개가 됩니다. SM 4개에 40 / 40 / 20+20 / 20+20으로 나누면 전체 시간은 40, 활용률은 \(160/(4\times40)=100\%\)가 됩니다.

Amdahl의 법칙

프로그램에 병렬화할 수 없는 부분이 있으면 프로세서를 아무리 늘려도 속도 향상에 상한이 생깁니다.

\[ S(p) = \frac{1}{f + \dfrac{1-f}{p}} \]

\(f\)는 병렬화할 수 없는 부분의 비율입니다. 전처리 같은 직렬 부분이 10%(\(f=0.1\))이고 GPU를 16장 쓰면 다음과 같습니다.

\[ S(16) = \frac{1}{0.1 + 0.9/16} = \frac{1}{0.15625} = 6.4 \]

GPU를 16장 써도 6.4배가 한계이고, 무한히 늘려도 \(1/f = 10\)배를 넘지 못합니다.

5-1. 임베딩과 거리: "비슷하다"를 숫자로 바꾸기

핵심은 간단합니다. 임베딩 모델이 코드나 문장을 숫자 벡터로 바꾸면, 비슷한 대상끼리 벡터 공간에서 가까이 놓입니다. 그래서 "비슷한 코드 찾기"가 "가까운 벡터 찾기"로 바뀝니다.

가까움을 잴 때는 주로 세 가지 방법을 씁니다.

척도식의미
유클리드 거리(L2)\( \lVert q-x \rVert = \sqrt{\sum_i (q_i-x_i)^2} \)작을수록 비슷함
내적(inner product)\( q \cdot x = \sum_i q_i x_i \)클수록 비슷함
코사인 유사도\( \dfrac{q\cdot x}{\lVert q\rVert \lVert x\rVert} \)방향이 같을수록 1에 가까움

실제로 계산해 봅시다

질의 벡터 \(q=(1,2)\)와 후보 \(a=(2,2)\), \(b=(4,0)\)이 있습니다.

척도q와 aq와 b더 비슷한 쪽
L2 거리\( \sqrt{(1-2)^2+(2-2)^2}=1 \)\( \sqrt{(1-4)^2+(2-0)^2}=\sqrt{13}\approx3.61 \)a
내적\( 1\cdot2+2\cdot2=6 \)\( 1\cdot4+2\cdot0=4 \)a
코사인\( 6/(\sqrt5\sqrt8)\approx0.949 \)\( 4/(\sqrt5\cdot4)\approx0.447 \)a

세 척도 모두 a가 더 가깝다고 판단합니다. 벡터 길이를 1로 맞춘(정규화한) 임베딩이라면 세 척도의 순위가 항상 같아집니다. 그래서 실무에서는 임베딩을 정규화한 뒤 내적으로 검색하는 경우가 많습니다.

예제가 작아서 nprobe=2는 오히려 brute-force보다 많지만, 실제 규모에서는 차이가 큽니다. 벡터 1억 개를 nlist=10,000으로 나누면 cluster당 평균 1만 개입니다. nprobe=10이면 centroid 1만 개 + 벡터 10만 개, 합쳐서 11만 번만 계산하면 됩니다. brute-force의 약 1/900입니다.

nprobe는 "속도 ↔ 정확도" 손잡이입니다. 늘리면 recall이 오르고 QPS가 떨어집니다. out-of-core에서는 nprobe가 곧 전송해야 할 cluster 수이기도 해서 전송 시간에 바로 영향을 줍니다.

5-4. 거리 계산 = 행렬곱: GPU가 가장 잘하는 계산으로 바꾸기

질의 m개와 벡터 n개 사이의 거리를 모두 구하려면 m×n번 계산해야 합니다. 이 계산은 아래 식으로 풀어 쓰면 대부분이 행렬곱이 됩니다.

\[ \lVert q-x \rVert^2 = \lVert q \rVert^2 - 2\,q\cdot x + \lVert x \rVert^2 \]

\(\lVert q\rVert^2\)와 \(\lVert x\rVert^2\)는 벡터마다 한 번만 계산해 두면 됩니다. 남는 \(q\cdot x\)를 질의 전체, 벡터 전체에 대해 모으면 행렬곱 \(QX^\top\)입니다. 행렬곱은 cuBLAS와 Tensor Core 덕분에 GPU에서 가장 빠르게 돌아가는 연산입니다.

실제로 계산해 봅시다

\(q=(1,2)\), \(x=(2,2)\)로 확인합니다.

STEP 1 \(\lVert q\rVert^2 = 1+4 = 5\), \(\lVert x\rVert^2 = 4+4 = 8\)

STEP 2 \(q\cdot x = 2+4 = 6\)

STEP 3 \(5 - 2\times6 + 8 = 1\). 직접 계산한 제곱 거리 \((1-2)^2+(2-2)^2=1\)과 같습니다.

import cupy as cp
# Q: (m, d) 질의,  X: (n, d) cluster 안의 벡터
qn = (Q * Q).sum(axis=1, keepdims=True)     # (m, 1)
xn = (X * X).sum(axis=1)                    # (n,)
D  = qn - 2 * Q @ X.T + xn                  # (m, n) 제곱 거리, 핵심은 Q @ X.T
topk = cp.argpartition(D, k, axis=1)[:, :k] # 질의별 가까운 k개 (정렬 전)

Faiss GPU 논문(Johnson 등, 관련논문 목록 IV-a)은 이 방식에 GPU용 top-k 선택(k-selection) 알고리즘을 더한 구조입니다. 주제 1의 4단계에서 직접 짤 CUDA 커널 후보도 이 top-k 선택 부분입니다.

6-2. Apriori: 후보를 줄여 가며 찾기

태그가 293개면 가능한 조합은 \(2^{293}\)개라서 전부 셀 수 없습니다. Apriori(Agrawal & Srikant, 1994)는 다음 성질 하나로 후보를 줄입니다.

Apriori 성질: 어떤 조합이 빈발하지 않으면, 그 조합을 포함하는 더 큰 조합도 빈발할 수 없다.
예: {시제, 관계사}를 같이 틀린 학생이 1명뿐이면, {시제, 관계사, 수일치}를 셋 다 틀린 학생도 1명 이하입니다.

알고리즘은 크기 1부터 한 단계씩 올라갑니다.

  1. 크기 1 항목집합의 support를 세고, minsup 이상만 남긴다 (L1)
  2. L1끼리 합쳐 크기 2 후보를 만든다 (C2)
  3. 후보의 support를 세고 minsup 이상만 남긴다 (L2)
  4. 크기를 하나씩 늘리며 반복. 후보 중 일부 부분집합이 빈발하지 않으면 세기 전에 버린다(가지치기)
  5. 새 후보가 없으면 종료

앞의 데이터로 끝까지 돌려 봅시다 (minsup = 2)

STEP 1 L1: 시제(4), 수일치(4), 전치사(2), 관계사(2) → 네 개 모두 통과

STEP 2 C2: 4개 중 2개를 고르는 6가지 조합의 support를 셉니다.

STEP 4 크기 3 후보를 만들어 봅니다. L2에서 첫 항목이 같은 쌍을 합치면 {시제, 수일치, 전치사}가 나옵니다. 그런데 부분집합 {수일치, 전치사}가 L2에 없으므로 support를 세지 않고 버립니다. 실제로 세어 보면 T1 한 명뿐이라 버린 판단이 맞습니다.

실제로 계산해 봅시다

STEP 2 {시제, 수일치}의 support: 두 비트열을 AND하면 둘 다 틀린 학생만 1로 남습니다.

\[ \texttt{11011}\ \text{AND}\ \texttt{11110} = \texttt{11010} \]

왜 GPU에 잘 맞는가

  • 컴퓨터는 비트 32개(또는 64개)를 한 번에 AND하므로 학생 32명을 연산 한 번으로 처리
  • popcount는 CPU와 GPU 모두 명령어 하나로 지원 (CUDA는 __popc)
  • 후보마다 같은 계산을 반복하므로 4-1절의 "thread 하나 = 후보 하나(또는 비트열 한 구간)" 구조와 맞음
  • FP-Growth처럼 포인터를 따라가는 트리 구조가 없어서 메모리 접근이 규칙적임

EdNet 규모로 계산하면 학생 784,309명의 비트열 하나는 약 98KB(32비트 단어 24,510개)입니다. 태그 293개 전체는 약 29MB라 GPU에 넉넉히 들어갑니다. 계산량을 키우는 것은 데이터 크기가 아니라 후보 수입니다(주제 2 표 참고).

import cupy as cp
# bm: (항목 수, 단어 수) uint32 비트맵,  cand: (후보 수, 2) 항목 번호 쌍
a = bm[cand[:, 0]]                          # (후보 수, 단어 수)
b = bm[cand[:, 1]]
# CuPy에는 popcount 함수가 없어서 ElementwiseKernel로 CUDA의 __popc를 호출
popc = cp.ElementwiseKernel('uint32 x', 'uint32 y', 'y = __popc(x)', 'popc')
support = popc(a & b).sum(axis=1)          # 후보별 support

위 코드는 후보 쌍 전체를 한꺼번에 메모리에 펼치므로 후보가 많으면 메모리가 부족합니다. 후보를 나눠서 처리하거나 AND와 popcount와 합계를 한 kernel 안에서 끝내는 것이 주제 2의 CUDA 커널 작성 단계입니다.

6-4. Apriori · Eclat · FP-Growth: 무엇을 병렬화할 것인가

빈발 항목집합 마이닝의 대표 알고리즘 세 가지입니다. 결과는 모두 같고, 찾아가는 방식만 다릅니다.

알고리즘탐색 방식데이터 표현GPU 적합성병렬화 논문 (관련논문 목록)
Apriori크기별로 한 단계씩 (너비 우선)수평 또는 비트맵좋음. 단계마다 후보 수가 많아 병렬화할 일이 충분함Fang 등(DaMoN 2009), YAFIM(Spark)
Eclat (Zaki, 2000)한 갈래씩 깊게 (깊이 우선)수직 (tid 목록 또는 비트맵)좋음. 교집합 연산이 비트 ANDZhang 등(J. Supercomputing 2013)
FP-Growth (Han 등, 2000)FP-tree라는 압축 트리에서 재귀 탐색트리나쁨. 포인터를 따라가는 불규칙 접근PFP(분산, Spark MLlib에 구현됨)

그래서 주제 2는 GPU 쪽은 비트맵 기반(Apriori·Eclat 계열), 분산 쪽은 Spark MLlib의 FP-Growth(PFP 방식)로 비교합니다. 알고리즘은 다르지만 출력은 같으므로 같은 입력에서 걸린 시간을 비교하는 것이 공정합니다.

GMiner는 무엇을 했나

교수님의 GMiner(Information Sciences 2018)는 비트맵 기반 GPU 빈발 항목집합 마이닝 방법입니다. 대규모 데이터에서도 GPU를 효율적으로 쓰도록 트랜잭션 비트맵을 블록으로 나눠 GPU로 보내며 support를 계산합니다. 탐색 전략으로 TFL(Traversal From the Last)과 HIL(Hopping from Intermediate Level)을 제안했는데, 정확한 동작은 제안 발표 전에 논문 원문으로 확인해야 합니다. 후속 연구 GMiner++(ESWA 2024)는 중복 계산을 줄였고 SGMiner(IEEE Access 2022)는 데이터가 GPU 메모리를 넘을 때 SSD를 활용했습니다.

교수님 본인 논문이므로 GMiner 부분은 발표 전에 반드시 원문을 읽고, 본인이 이해한 범위만 슬라이드에 넣습니다. 수업 자료의 "명확하게 이해하지 못한 내용은 기호 하나라도 포함하지 말 것"에 해당하는 부분입니다.
